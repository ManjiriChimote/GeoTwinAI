# GeoTwinAI — Implementation plan

## Product scope and constraints
Build a complete, inspectable Nagpur urban-planning workspace—not a static dashboard—grounded in the uploaded master prompt, five reference screenshots, project source, satellite/infrastructure data, map and report. Add a narrowly scoped source-backed public landing page because the user requested SEO, while keeping all data-management/workspace APIs and content protected. Preserve the 5-region analytical model (not official wards), existing useful project logic and source record attributes. The project already has a complete React/TypeScript/Vite/Express/tRPC/Drizzle starter; managed server and MySQL-compatible database are enabled. The current runtime is port 3000. The existing database is shared by development and publication; use additive schema changes, idempotent initialization, and never truncate/replace data automatically. MySQL has no PostGIS extension here: retain WKT/GeoJSON as validated source geometry and normalized longitude/latitude columns, indexed for viewport filtering; describe this deviation instead of claiming PostGIS. Require first-party Manus OAuth for the workspace and its API; honor the user's chosen private access policy: signed-in collaborators can read/analyze/report, but only the configured project owner may change shared datasets. The owner match requires `OWNER_OPEN_ID` in a protected project environment value; if unset, changes remain locked. Hash conversation IDs with the verified account OpenID so chat records cannot be read across users. Use database-backed data, history, analyses and conversation records; no browser-local storage as the system of record.

The archive contains full source data and a master build prompt; five PNG UI refs; existing Python Streamlit applications (`app.py`, `GeoTwinAI_Physical_Digital_Twin.py`), OSM fetch/config/pipeline scripts, a Folium interactive HTML, a PDF report, clean and duplicate processed CSVs, raw and processed infrastructure files, satellite images, raster/spatial index CSVs, and a pickle model. Useful source logic and schemas were inspected. Do not run/rely on unsafe pickle deserialization. Do not import duplicate `_1` files or interpret conflicted merge-marker rows in a summary file as measurements. Recompute record counts from actual data, track source vs valid/mappable counts, preserve source values, and show attribution and caveats. Example report/CSV discrepancies (including conflicting NDVI and water counts) make provenance important. The supplied regional feature table is explicitly count/index data, not a population denominator or proof of underserved communities. Satellite dates/cloud metadata vary by dataset; the analysis area is not a verified municipal boundary.

## Implementation approach
- Extend the managed React 19, TypeScript, Vite, Express, tRPC and Drizzle/MySQL app already initialized in `/home/ubuntu/geotwin`. Keep typed application code in `client/src/`, backend in `server/`, shared schemas under `shared/`, and additive Drizzle schema/migrations under `drizzle/`.
- Implement database tables for dataset metadata/registry, geospatial features (original attributes as JSON text; WKT/geometry type; nullable validated WGS84 longitude/latitude; data category and source region), import history, analysis/report runs, and Geo conversation history. Add ordinary category, dataset, region and latitude/longitude indexes supported by managed MySQL. Apply migrations against the existing managed database without dropping the supplied users table.
- Seed the database, once and idempotently, from compact gzip/NDJSON distilled from the non-duplicate clean source files in the provided archive. Include the real core Nagpur OSM records (buildings, roads, hospitals, schools, parks and water bodies) and appropriate processed raster samples/records for built-up, green-cover, flood and Sentinel-2 NDVI. Keep small verified source summary metadata. Preserve nonempty original attributes. Distinguish full source row counts, invalid-coordinate rows and indexed/mappable rows. Preserve environmental `Nagpur` scope rather than fabricating North/South/East/West/Central labels when absent. Provide a read-only viewport API with a strict record limit and normalized geometry for a Leaflet map; large road/raster datasets are not transferred in full to the browser.
- Provide validated CSV and GeoJSON upload/preview/commit workflows (with schema/field matching, WKT/coordinate discovery, CRS/range validation, duplicates/missing coordinates, progress/history, safe replacement rules, activation and actionable errors). Batch/chunk parsing and inserts; uploads require an explicit import confirmation. GeoPackage may be documented as not directly supported if reliable safe conversion is unavailable; do not imply success for unsupported formats.
- Add safe, parameterized server APIs/tRPC procedures for summary, feature viewport/filter/search/pagination, datasets and history, uploads, analyses, report export and chatbot turns. Deterministic queries supply exact values; the managed LLM may interpret verified results through the server service API. Never execute model-generated SQL or provide private credentials to the browser. When managed AI is absent/fails, return a clearly labeled evidence-based local query answer. Conversation history is persisted safely.
- Render a real interactive Leaflet geographic map (with accurate feature-source attribution, genuine pan/zoom, fit, map layers, feature click inspection, filtered viewport queries, legend, loading and missing-data states). Draw a restrained local coordinate grid beneath the actual supplied source geometries rather than requesting hosted raster basemap tiles: the Preview project is access-controlled, and public tile providers impose their own access/traffic conditions. OpenStreetMap-derived source features remain credited; popups show file and attribute provenance. The reference warm map panel is an actual map, not a decorative architectural image. Use the provided Nagpur study coordinates only while valid.
- Use computed database values and source summaries for overview, regional comparisons, data completeness, facility/road analytics, transparent rule-based “assessment priority” indicators, data-quality details, and PDF/CSV report generation. Every displayed statistic has a source and methodology. No real-time operations, official conclusions or validated ML performance are claimed. Reports state data date, sources, methods and limitations.
- Serve the SEO landing page as meaningful initial HTML at `/` with a distinct private, noindex Manus-authenticated workspace at `/workspace`; publish canonical, Open Graph, social-card and JSON-LD URLs only after `GEOTWIN_PUBLIC_ORIGIN` is set to an actual public HTTPS domain. Until then, keep preview/no-domain robots blocked; once configured, permit only `/` and keep `/workspace`/API routes out of indexing and the sitemap. The sitemap lists only the landing page. This is SEO preparation, not a promise of immediate search-engine ranking or a public launch.
- Synchronize the complete page route manifest, maintain port 3000, expose `/api/health`, keep request origins relative, and provide `.env.example`, migration/seed instructions and a Windows/VS Code quickstart. Document database/AI/map dependencies and dataset provenance. All UI actions should have a visible outcome.

## Design system (Physical Digital Twin / architectural model)
- **Design movement:** architectural maquette and contemporary editorial cartography; the measured restraint of a studio drawing set, not a generic SaaS dashboard.
- **Core principles:** data before decoration; spatial context stays visible; calm editorial hierarchy; disclose uncertainty rather than simulate certainty.
- **Color philosophy:** paper ivory (`#F5F2E9`) sets a tactile, studied baseline; stone beige (`#EAE5DA`) distinguishes the region rail; graphite (`#303238`) grounds hierarchy; muted blue (`#527C8C`) marks analytical labels; sage/olive (`#91A58A`) distinguishes land and vegetation; terracotta (`#C66A5B`) appears only for active/attention states; borders `#D9D2C4`. Map colors remain legible in low saturation; avoid gradients/neon.
- **Layout paradigm:** fixed, pale stone desktop rail (~320 px) for region/nav; wide paper workbench with an asymmetric map-led primary composition, narrow contextual column, and editorial rules between section headers. Collapse rail into a keyboard-accessible mobile drawer; stack map and information cards, not an all-center generic card grid.
- **Signature elements:** fine gridded map datum and subtle contour-line strokes; coral active-navigation dot; letterspaced blue section/corner labels and mono-coordinate readouts. The friendly Geo Earth illustration uses subdued blue/sage landforms and subtle contour references, in an intentional small assistant role rather than hero decoration.
- **Interaction philosophy:** direct manipulation; map layers/query/focus visibly update their corresponding legend, counts and controls; explain disabled/unavailable states; preserve active session chat; keyboard-first controls and clear focus.
- **Animation:** 180–300 ms ease-out for route/section, drawer/chat, selection, and cards; no bouncing/continuous motion, no artificial loading progress; use real upload progress; respect `prefers-reduced-motion`.
- **Typography:** Manrope for display/brand, Inter for dense UI and body, IBM Plex Mono for coordinates/technical values; uppercase labels 10–11 px/0.13em tracking; body 14–16 px with 1.55 line-height; use reserved 28–36 px section titles rather than giant hero headings.
- **Brand essence:** “A measured, evidence-led living model for the people planning Nagpur.” Personality: grounded, exact, humane.
- **Brand voice:** concise, calm, factual; label interpretation and uncertainty. Example: “The map is ready; 46,052 building records are indexed, 45,9xx with valid coordinates.” “A lower count is a prompt to check coverage—not a confirmed service gap.”
- **Wordmark & logo:** custom GeoTwinAI lockup with a small mapped-city/contour glyph: rounded surveying aperture rings around a simple urban block; no emoji/default-font-only logo.
- **Signature brand color:** muted survey blue `#527C8C`.

## Planned initial route behavior
The public static landing page is `/` and contains no private row-level data. The first-party Manus OAuth SPA is `/workspace`; all GeoTwinAI APIs require authentication and workspace responses carry `noindex,nofollow`. Overview / Explore / Analyze / Intelligence / Report / Data Management / Settings remain internal workspace views. Only those two HTML pages are in `manus-routes.json`; API endpoints are explicitly excluded. The public-origin value is intentionally blank until a user-controlled domain and public hosting target exist; there is no canonical URL, sitemap URL, or search-index access before then.
