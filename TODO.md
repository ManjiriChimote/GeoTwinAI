# GeoTwinAI implementation outcomes

## Private identity and shared-database access policy
- Require first-party email/password signup and login for the workspace and every protected GeoTwinAI data API. Persist account data, salted password hashes, terms acceptance and revocable expiring server-side sessions; use CSRF protection for mutations. Require acceptance of the current Terms & Conditions at signup and provide an accessible Privacy Notice. Email verification and password-reset email are not configured and must not be implied. Signed-in collaborators may explore, analyze, create reports and use their own account-isolated Geo conversations; only the explicitly configured project owner may upload, activate or delete shared datasets. New signup never grants admin rights: writes remain locked until the protected `GEOTWIN_OWNER_EMAIL` and `GEOTWIN_OWNER_ACCOUNT_ID` both match the same account. Keep the preview at owner/team scope; do not change the access policy or publicly expose sensitive records without permission.
- The user first chose “Manus sign-in for all; project owner manages data,” then later requested a normal login/signup page and Terms & Conditions. The later request supersedes only the login provider; owner-only shared-data access remains required.

## 1. Shared architectural interface and navigation
- Reproduce the supplied “Physical Digital Twin” visual direction closely: warm paper/ivory background; light stone-beige sidebar; graphite typography; muted-blue labels; sage/olive map accents; restrained terracotta; fine borders/grid/contours; ample whitespace; refined sans serif; rounded panels; restrained shadows and subtle hover states. Avoid dark neon, purple/blue gradients, excessive glassmorphism, unnecessary decoration, crowded KPIs, generic AI illustrations, giant headings, constant floating/bouncing motion, unrelated stock photography, and a generic dashboard appearance.
- Keep a persistent left sidebar approximately 320–345px on large desktop with selectable North, South, East, West and Central analytical regions; GeoTwinAI identity; Overview, Explore, Analyze, Intelligence and Report navigation; and accessible Data Management/Settings. Each of the North, South, East, West and Central buttons must respond to click/tap, clearly expose which region is selected, and filter relevant data, charts and map features using matching source-region labels where geographic region information is present. Regions are analytical project regions, not official wards. Collapse the sidebar cleanly on mobile.
- Header reads “PHYSICAL DIGITAL TWIN” and “OBSERVE · EXPLORE · UNDERSTAND”; include settings/overflow and Deploy only if deployment functionality is implemented. Use minimalist circular navigation indicators and a restrained coral/red active indicator.
- Overview includes a genuine interactive Nagpur GIS map, valid map-center coordinates only when available, functioning Buildings/Roads/Green/Water/Risk layer controls and matching legend, “DESIGN LANGUAGE” card with “Like an architectural model, not a game.” and its supporting explanation, “THE STORY” card with the specified data → analysis → AI → decision text, live source/data/import status, computed city statistics, and shortcuts to Explore, Analyze and the assistant. The map remains the visual centerpiece; it is not a static picture or an invented 3D city. After the user's latest request, the map also exposes independent controls for every available GIS category, including Buildings, Built-up, Roads, Hospitals, Schools, Parks, Green cover, Water bodies, Flood risk and NDVI; those stored categories are shown by default when available.
- All pages share the same design language; meet accessible-label, keyboard-navigation, visible-focus, appropriate-contrast, responsive and reduced-motion requirements. Buttons and controls produce real outcomes; provide clear loading, error, empty, unavailable and no-record states. The initial map view covers all project regions, while region controls retain each analytical region plus All regions. Prevent duplicate analysis requests and disable/label map-fit controls when no records are loaded. Use subtle 180–350ms transitions for navigation, map/filter/charts/chat/import/details only; progress is real, never simulated.

## 2. Interactive GIS and transparent analysis
- Use a reliable GIS mapping library and a geographically correct interactive Nagpur map over actual project geometry. Credit OpenStreetMap-derived records while making clear that their source files—not a live OSM basemap—provide this data. The map's restrained local coordinate grid is explicitly not a street, satellite or administrative basemap; avoid third-party raster tiles unless their current provider terms fit deployment access/traffic. Implement pan/zoom, search by feature name, category or preserved source attributes, category and analytical-region filters, layer visibility, legend/visible-layer status, fit-to-data extent, feature popups with actual attributes/provenance, loading/error/empty states and a responsive view. Every layer pill toggles real database records; unavailable layers open upload. Serve viewport-bounded/database-filtered results for large datasets; do not bundle full road tables in browser code.
- Accept and validate WKT POINT, LINESTRING, POLYGON and MULTIPOLYGON, GeoJSON, varying field names, latitude/longitude, region/category fields, optional attributes, missing values, duplicate features, inconsistent region labels, invalid and mixed geometries, missing/unreliable coordinates, large lines, Unicode/Marathi and uncertain/proposed-site attributes. Validate CRS and coordinate ranges and do not silently assume every coordinate uses the same CRS. Store uploaded source attributes and geometry without destruction; index supported server-side fields for viewport/search filters.
- Provide data-driven facility distribution by region, infrastructure density, region comparisons, candidate underserved-area assessment, school/hospital accessibility, road connectivity where available, proximity/buffer analysis, data quality and coordinate completeness, and development-suitability indicators. Apply the selected analytical region to regional proximity results; All regions uses the full study dataset. State the question, required datasets, methodology/assumptions, computed result, chart/map and limitations/missing data. Never infer “underserved” solely from fewer observed features when dataset coverage is incomplete; do not call a count-based indicator a verified planning conclusion.
- Display environmental indices/land cover, satellite, built-up, green-cover, heat and flood information only when relevant supplied records are actually available; disclose dataset date/cloud/source/scope. Do not invent risk values or trends or represent any historical/real-time animation when no time series exists. Use muted sage, blue, terracotta and graphite for live charts.

## 3. Data management and durable database
- A managed server and persistent managed database must exist. Persist dataset registry/metadata, imported geospatial feature records, import status/history, analysis runs/results, report metadata and appropriate Geo conversation history so data survive refreshes and restarts. Database changes are additive and safe; preserve existing database records, users and supplied user data. Use indexes, backend pagination and parameterized queries. Do not rely primarily on browser state, temporary file storage, source inventories, or filenames for facts.
- Data Management provides project-owner-only file selection/upload, dataset name/category, schema/sample preview, geometry/coordinate/field detection, validation/error reports, explicit import confirmation, progress/completion status, persistent import history, record counts/data-quality metrics, safe replacement/re-import, activation/deactivation and actionable unsupported/malformed-data messages. Signed-in collaborators may inspect but cannot modify shared data; matching server-side permission checks protect write APIs. Support CSV and GeoJSON; support GeoPackage only if safe and feasible, else explicitly state it is not accepted and document conversion. Keep app useful before uploads.
- Validate upload type, size and content. Process large CSVs (especially roads) in chunks/batches with progress; support long lines. Preserve original columns/attributes and normalize only query fields. Distinguish uploaded/not uploaded, processing, no records, invalid records and available spatial records. Never report an inventory as if it were records.
- Seed from supplied actual non-duplicate source data without copying every archive artifact or the duplicate `_1` files. Show source-record counts separately from records with valid map coordinates. Preserve and disclose source provenance/methodology. Exclude or flag merge-conflict-corrupted summaries, never treat them as valid values. Do not load or execute the supplied pickle model.

## 4. Grounded Geo Planning Assistant and explainable intelligence
- Provide a compact friendly floating Geo assistant, inspired by the finalized Earth-companion conversation but still professional: warm off-white panel, muted-blue/sage accents, rounded bubbles, subtle entrance/message animation, loading/thinking state, signed-in-account-only conversation history, helpful empty state and suggested questions: “Summarize the available infrastructure in Central Nagpur.” “Show hospitals on the map.” “Compare schools across the five regions.” “Which areas may need further infrastructure assessment?” “Check the quality of my uploaded datasets.” “Explain the current development-priority results.”
- Use a real server backend service. For exact figures, query the application database through deterministic safe tools; use a model only to interpret verified results and explain findings. The assistant answers from actual datasets, summarizes counts/categories/regions/quality, compares areas, explains methodology, suggests analysis, highlights relevant layers/features, supplies working “View on map”/“Open analysis” actions and reports when information is unavailable/unreliable. Respect selected region/dataset context where relevant. Do not execute arbitrary model-generated SQL. Distinguish facts, estimates and recommendations. Handle API timeout/error/rate limits/empty results honestly; never pretend AI is connected when credentials are absent. Provide a working local data-query mode where feasible.
- Intelligence supplies regional planning summaries, evidence-based explainable High/Medium/Low assessment priorities, potential coverage gaps, data-quality warnings and next analyses, with a reason for each recommendation. Use a transparent configurable rule-based baseline and label it accordingly unless a trained, validated model is demonstrably available. Never claim an unvalidated model or authoritative government decision.

## 5. Report, setup and operation
- Users can choose region, datasets and indicators; generate a computed regional planning report; review tables/charts; export CSV and PDF. Reports derive from actual imported database records/computed analyses and include report date, source datasets, methodology and limitations. Empty data produce explicit notices, not fabricated output.
- Provide `README.md`, `.env.example`, deterministic migrations, secure database setup, selected-host deployment instructions, and clear Windows/VS Code local-development workflow. Document source attribution and current map-source/provider decision; do not invent integrations with MahaBHUMI, MRSAC, Asset Mapping, official land records, CM programs, UAV/LiDAR or unavailable APIs.
- Respect the stated project’s data-provenance limitations: Nagpur’s study box is not necessarily an administrative boundary; satellite observations depend on season/atmosphere; provider metadata is scene-level; flood/heat outputs depend on inputs/methods; infrastructure should be checked against authoritative data; ML inference depends on representative training and validation data; future dates are unknown before new observations.
- Provide a valid `GET /manus-routes.json` static page-route manifest (not APIs/assets), and `/api/health` success. Keep browser-visible URLs relative and do not expose secrets.
